## 3. PR问题：画图补零与真实错误分开处理

PR横轴是Recall，不是置信度。当前项目`ultralytics/utils/metrics.py::compute_ap`在最大观测召回处追加precision=0，
随后补至Recall=1，因此会出现贴地尾段。这是本地实现的端点处理，不能直接解释为高置信度预测全部错误。
本次**没有改动AP计算、插值、置信度或NMS阈值**。另外根据回传的真实阈值点绘制了
[不补零PR诊断图](E_V9_REVIEW_20260915/V8_empirical_PR.svg)，仅作诊断，不替换正式PR/AP。

V8_03统一640评估、conf=.25、mask IoU=.5：

|模式|极小果实检出/161|全部TP/1049|背景FP|P≥90%时的召回|conf=.001最大召回|
|---|---:|---:|---:|---:|---:|
|整图|36|842|151|77.121%|91.420%|
|细切片＋trusted-mask融合|101|939|406|81.030%|96.282%|

整图207个漏检中125个来自极小目标，占60.4%。切片后极小目标仍漏60个，背景FP却更多。
所以输入分辨率确实是瓶颈之一，但“只要召回拉满”不成立：大量低分误检拖低了真实PR尾端。
单纯提高阈值会损失召回；仅改曲线终点不能改善模型。

V8_03原始混淆矩阵显示TP846、FP164、FN203，其权重/验证口径不应与上面的best_mask成对评估混算。
单类别矩阵只能区分目标与背景，不能证明164个FP全是绿色叶片。需要在误检图上标注叶片、枝条、天空等来源，
并按遮挡深凹、接触间隙和单图尺度跨度分层，才可声称解决“颜色混淆/拓扑冲突”。

## 4. V9的结构和方法

### 检测保留，掩膜分流

主干保留已验证底座：浅/中层C3k2，C5内层partial mixing，SPPF+C2PSA。此次**没有声称换了全新主干**；
V8上下文主干不足以支持继续沿该方向扩大改动。检测颈部保留P3/P4/C5非对称拓扑，以及P4的空间重建。

新`EV9MaskNeck`从原生C4和C5提取16通道上下文，进入独立掩膜细节路径。
令S为上采样语义，D为原有P2细节，L=AvgPool(D)，H=D−L；门控由[S,L,|H|]产生两个softmax权重，
输出D′=D+tanh(a)[w1(S−L)+w2 DWConv(H)]，a初始化0.1。
它将语义差异与局部残差分别处理，学习抑制无语义支持的背景纹理。
高频不等于果实，绿色也不是硬编码的判别规则；效果仍须验证。它是一遍前馈修正，不是PID控制器或稳定性证明。
检测细节回传发生在这项新修正之前，固定权重下改变新门控不会改变检测输出，测试已验证。
训练时仍共享主干梯度，不能宣称两个任务在优化上完全独立。

### 换掉宽Proto，不缩掉必要的检测路径

新`EV9CompactProto`替换原有宽原型解码：P3投影32通道→上采样P2→加16通道细节的投影→DW3×3+PW1×1→32个mask basis。
再接已有stride2相位细节修正。实例系数塔不变，最终mask仍由系数和共享原型组合。
这是掩膜融合/解码计算分配的调整，不是把额外注意力串在原网络后面。

### 两项训练监督各自有对照

- Tiny Dice，增益0.25：补充监督可见面积<256输入像素且已有正样本的小实例。每GT平均系数后计算一个局部Dice，避免重复anchor权重。
  原BCE仍监督所有正样本。它不凭空恢复没有正样本或已栅格消失的GT，不能单独保证提高召回。
- 背景质量监督，增益0.1：现有质量分支原来只学习正样本IoU，加入每图至多32个分类分数较高的负anchor，质量目标为0。
  排除所有GT框及其8像素外扩区域，包括未分配的极小GT，降低误惩罚真实果实的风险。仍要求标注可靠。
  不新增推理分支；质量评分仍保留0.5下限，不把低质估计直接乘成零。该设计借鉴质量感知排序，**不是VarifocalLoss原式复现**。

保留可见边界0.5、邻实例0.25、CP0.3，绝不使用圆形填充、凸包补全或amodal标签。
AdamW仍为统一优化器；只在09组把线性学习率改成余弦，以判断优化日程是否有效，不混入架构结论。

## 6. 训练方式与固定设置

上传最新整个`1_SEVER/code/ultralytics-main-new`代码副本，不能只传YAML。无需装Mamba、Detectron2或额外DCN。
打开根目录`RUN_CITRUS_E_V9.py`，改好自己的DATA、DEVICE、PROJECT，然后在VSCode选训练环境，点击右上角三角形。

```python
DATA = "/data/sxq/datasets/orange_yolo/data.yaml"  # 你的清洗数据，不按目录名推断身份
DEVICE = "1"
SUITE = "all"  # 十组；priority只跑01/02/03/04/08
EPOCHS = 300
DRY_RUN = False
ONLY = ""  # 例如 V9_08_complete，可单独完整复现该模型配方
```

也可以在主代码目录直接前台运行：

```bash
python RUN_CITRUS_E_V9.py
```

cache=True，amp=False，batch16，workers4，imgsz640，seed42，AdamW lr0=.001/lrf=.01，momentum=.937，weight_decay=.0005，
mask_ratio2，原有warmup/增强/验证设置保留。正式配置见`protocols/citrus_e_v9.yaml`和`citrus_e_v9_suite.py`。
09是唯一cos_lr=True组。cache缓存可能占用较多RAM，也不保证位级确定性；不要为追求速度偷偷切换AMP或batch。

首次可将DRY_RUN=True只检查构建，看到BUILD OK后会正常退出；检查后必须改回False才训练。
前台顺序运行，不用nohup，不设GPU占用锁；Ctrl+C停止队列，不会自动开始下一模型。物理GPU1被映射成进程内cuda:0是正常现象。
已完成运行可跳过，未完成目录不会覆盖；需要跳过半途模型可用ONLY列出其他模型，或换新PROJECT。
YAML能够走官方`YOLO(yaml)`构建/训练；但仅调用裸`model.train()`不会自动带上切片混合数据、CP和配套统一评估。
要单模型公平复现，优先使用同一入口的ONLY，而不是另写一份不同超参训练代码。
