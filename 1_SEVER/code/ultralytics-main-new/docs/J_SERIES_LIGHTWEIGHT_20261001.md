# 精度确认后的轻量化路线：以实测预算而非模块标签作取舍

日期：2026-10-01。J11/J17 都是候选，未证明具有最优精度或速度。以下后三阶段为计划，不是已经实现的剪枝/蒸馏/量化功能。

## 1. 先明确“轻量化”的优化目标

最终要比较的是同一服务器、同输入/精度/后处理条件下的 Mask AP、Recall、batch1 延迟、训练步耗时、峰值显存、Params 和 FLOPs。**训练快、推理快、参数少是不同目标。** 当前 CPU 测量中 J17 并未证明比 YOLO11n 更快，不可把它提前当成最终轻量化成功方案。

选择冻结的精度参考 A 后，定义待确认的容许损失 δ 和小目标召回下限 r：

\[
\min_{\theta,\mathcal A}T_{GPU}(\mathcal A,\theta),\quad
\text{s.t. }AP_{mask}\ge AP_A-\delta,\;R_{tiny}\ge r,\;M_{peak}\le M_{budget}.
\]

δ、r、部署目标设备应在后续压缩实验前确定，不在看过测试集之后调整。先报告完整 Pareto 前沿，不能只挑一个 FPS 高而极小目标漏检严重的模型。

## 2. 当前已经做的第一阶段

| 候选 | 参数 | 估算 GFLOPs@640 | 作用 |
|---|---:|---:|---|
| J00：同配方 YOLO11n | 2.843M | 10.356 | 精度与速度对照 |
| J11：综合结构 | 1.075M | 5.216 | 先验证细节、融合与辨别能力 |
| J17：窄预算结构 | 0.709M | 3.875 | 测试语义宽度压缩是否可接受 |

以上 GFLOPs 统一为 full640、nc1、THOP+差分上下文矩阵乘法估算，非全算子精确计数。J17 相对 J00 的参数约少75.1%、估算计算约少62.6%，**不等于训练耗时或部署延迟下降对应比例**。

窄化优先压缩深层语义与融合通道，而不是先删除极小目标所需的 stride2/4 细节。P3/P4/P5 保留；某个尺度是否可以移除需单独消融，不把“当前关注小目标”等同于“深层大感受野没有用”。

## 3. 为什么 Light 曾经“参数少但特别慢”值得警惕

对常规卷积，MAC≈HW×k²×Cin×Cout；等比例缩窄 r 时该项约为 r²。深度卷积约为 HW×k²×C，缩窄仅约 r。固定宽度 mask 原型、候选数、重采样和损失循环不会随主干宽度平方下降。

理想设备下，单算子耗时受至少两种预算约束：

\[
T\gtrsim \max(F/P_{peak},\;B/W_{peak}),
\]

其中 F 是操作量、B 是实际必要的数据传输量；实际还包含 kernel launch、算子串行与调度损失。这是硬件预算估计，不是整网速度定理。大量小卷积/深度卷积、空间重排、高分辨率中间张量和重复切片都可能使低 FLOPs 网络更慢。不能在没有服务器 profiler 时认定某一个算子就是历史慢训练的唯一原因。[MobileNetV4](https://arxiv.org/abs/2404.10518) 的设备导向设计也是需要实测而非只看参数的参考。

J 的 stride2 原型有32×320×320元素，是 stride4 的4倍；不能为“保小目标”无节制加高分辨率通道。首先在 J04/J05 的同协议结果中判断这一代价是否值得。

## 4. 已实现的服务器测速入口

打开 `RUN_BENCHMARK_CITRUS_J.py`，设置物理 DEVICE，保持 IMAGE_SIZE=640、TRAIN_BATCH=16，点击 VS Code 三角形或前台 `python RUN_BENCHMARK_CITRUS_J.py`。默认逐组 J00/J11/J17，warmup5、20次重复，FP32、AMP=False、TF32=False。

输出 `benchmark.json` / `benchmark.csv`，记录：未融合与 Conv-BN 融合后的 batch1 前向、包含实际 criterion/反向/AdamW 的训练步中位数和 p90，以及 CUDA 基线、总峰值和新增峰值显存。总峰值包括常驻合成训练输入；融合测量还持有原始网络，不能不看基线就将其认定为部署显存。融合后另做输出数值一致检查。不会自动降 batch、降低输入尺寸或切换半精度来制造速度优势；OOM 如实记录。

**测速使用相同的 GPU 常驻合成输入、每图8个可见实例，包含小尺度支持，不使用测试集。** 不包含读图、增强、传输、NMS、掩膜裁剪、EMA、切片拼接和验证，因此不能把它的倒数写成部署端到端 FPS，也不能据此推算一轮训练时间。训练步仅使用单参数组 AdamW，不是完整 trainer 精确重放。GPU测速时不要与另一训练并行，否则不能用于归因。

当前仅通过 CPU 小尺寸功能测试；真实640 GPU测量要由服务器执行。若 kernel 微测正常但整轮慢，应分别计时数据加载、训练、验证；不要继续盲目换主干。

## 5. 第二阶段：冻结精度结构后做任务感知压缩

先用验证集选出真正有效的精度路径，再压缩深层语义/融合宽度和重复次数。结构化通道移除必须同时处理相加、拼接、分组卷积、相位重排、四分之一通道划分和 head 接口的依赖。参考 [DepGraph](https://openaccess.thecvf.com/content/CVPR2023/html/Fang_DepGraph_Towards_Any_Structural_Pruning_CVPR_2023_paper.html)；当前 **没有把自动剪枝直接接到 J**，自定义模块需定制依赖规则并重新验证 YAML/前反向。

优先对照：保留高分辨率空间尺寸而降低中间宽度；避免同时改 mask 栅格、主干、损失和优化器。对小目标 Recall、遮挡凹口与接触 split/merge 做非劣效性检查，不只用总体 AP 抵消难例退化。

## 6. 第三阶段：让有效精度教师教窄学生

冻结同一正式划分、同协议训练的最好教师；学生仍是一个推理网络，教师只在训练使用。参考 [Channel-wise KD](https://openaccess.thecvf.com/content/ICCV2021/html/Shu_Channel-Wise_Knowledge_Distillation_for_Dense_Prediction_ICCV_2021_paper.html) 的空间分布蒸馏思路，而不是复用旧泄漏结果权重当教师。

不能直接逐通道 L2 对齐任意 mask 原型：若系数 A 与原型 P 同时变换为 AS⁻¹ 与 SP，则 AP 不变，原型通道并不唯一。更合理的候选是同一 GT 对应的最终软 mask / 边界分布，以及经过可学习对齐后的细节特征；教师漏检不能作为删除学生 GT 监督的条件。先独立验证教师是否真的在 tiny/低对比子集更好，再决定是否蒸馏。

这一阶段尚未编写训练代码，因为没有 J 正式教师结果；现在提前做蒸馏会把教师能力、结构压缩和损失变化混在一起。

## 7. 第四阶段：部署优化与最终报告

先做固定统计下 Conv-BN 融合，再在独立导出协议中测试 FP16 / INT8；训练仍固定 AMP=False，不把部署精度设置混入架构消融。量化必须检查 tiny 支持、边界与召回退化，不能默认INT8安全。

最终报告未融合/融合、输入尺寸、batch、精度、硬件、warmup、重复次数、NMS与mask处理、是否切片，以及训练步与整轮耗时。选择三seed AP/R 稳定且端到端延迟合理的模型，而不是把最大的综合候选强行称为“最佳网络”。
